# coworker 企业 AI 助手 · 产品方案（三层形态）

- 版本：0.1.0（草案，待评审）
- 关联：DESIGN.md（pi-coworker 技术设计）
- 定位：回答「面向非开发者全体员工，企业 AI 助手应该是什么形态」——结论是**分层**，不是单一客户端。

## 1. 背景与目标

现有 pi-coworker 是一个 pi 包（CLI/插件形态）：通过 lark-cli 编排飞书，提供入职引导、权限申请、知识问答、安全治理。它面向**开发者/IT**是合适的，但面向**非开发者全体员工**（HR/财务/销售/运营…）存在根本摩擦：终端、命令、JSON 配置都不成立。

本方案定义三种形态的边界、身份模型、部署与成本，给出分期路线，让团队先对齐方向再投入。

### 目标

1. 覆盖全员：非开发者零学习成本使用（问、办、导）。
2. 复用内核：三种形态共享同一套 coworker 核心（知识检索、权限目录、安全规则、审计）。
3. 可控成本：按场景选择最省力的形态，避免"为所有人生造一个桌面 App"。
4. 合规清晰：明确数据在何处、用什么身份、谁可审计。

## 2. 用户分层与场景

| 人群 | 典型场景 | 形态 |
|---|---|---|
| 开发者 / IT | 写代码、跑数据、自动化、公司资源操作 | **pi CLI + 插件** |
| 全员（多数） | 查制度/百科问答、申请权限、入职引导 | **个人本地 Bot**（飞书内交互，零安装） |
| 全员（少部分） | 本地文档处理、个人数据分析 | **个人本地 Bot**（local 模式可开本地工具） |

## 3. 形态与功能边界

### 3.1 形态 A：pi CLI + pi-coworker（开发者，保留）

- 边界：开发者工作流（cwd、git、bash/read/edit/write、本地文件）。
- 策略：不动，继续演进。

### 3.2 核心形态：个人本地 Bot Agent（推荐默认）

**后台常驻 agent 跑在员工本机，用户在飞书里私聊自己的 Bot**：

- 交互全在飞书：自然语言问答、权限申请卡片、入职指引卡片，零安装。
- agent 在本地：用**用户自己的 lark-cli 身份 + 自己的 LLM provider**，个人上下文（我的权限/我的文档）直接可用；工作目录=本机，可做本地操作（可选开启）。
- 通过 lark-cli 与飞书能力捆绑：个人 Bot 应用收消息、user 身份读个人数据、卡片处理审批/直授。
- 前置：每人一个个人 Bot 应用（setup 引导创建）；本机开机 + 守护进程运行；Bot 设仅本人可用。

同一守护程序（`agent/`）以 `RUN_MODE` 支持两种部署：

| RUN_MODE | 位置 | 身份 | 工具集 | 场景 |
|---|---|---|---|---|
| `local`（默认） | 本机 | 用户 | 全 coworker（可开本地工具） | 个人助手 |
| `server` | 服务器 | bot | 只读子集 | 全员共享知识机器人（7×24） |

### 3.3 形态 C：桌面 GUI（已降级为可选项）

- 飞书内交互已满足日常，GUI **不再是必选项**；仅保留为守护进程的**托盘/启动器**（控制启停、看状态）。
- 若保留 Tauri 壳：复用 agent/ 的本地后端 + pi RPC，本机用户身份。

## 4. 身份模型对比（决定形态的关键）

| 需求 | 本机用户身份（GUI/CLI） | 服务端 bot 身份（机器人） |
|---|---|---|
| 读公司百科/制度 | ✅ | ✅（需 bot 有读权限） |
| 申请知识库/文档权限 | ✅ 直授/审批 | ⚠️ 只能发审批链接/向 owner 申请，不能代加成员 |
| 查看/管理"我的"资源 | ✅ | ❌ 需 OAuth 用户授权 |
| 本地文件/文档处理 | ✅ | ❌ |
| 隐私边界 | 数据在本机，用员工自己的飞书授权 | 对话与数据过公司服务器，需明确审计 |

**结论**：能走"员工本人身份"的本地形态（GUI/CLI）覆盖个人化操作；bot 形态用应用身份覆盖"全员只读知识"类。二者互补，共用内核。

## 5. 飞书机器人：实现路径（已选 B1）

> **决策（2026）：选 B1 —— pi agent（RPC 常驻）**，服务器端运行完整 pi-coworker agent。

### 5.1 B1 vs B2（决策记录）

| 维度 | **B1：pi agent（RPC 常驻）** | **B2：轻量服务（LLM + lark API）** |
|---|---|---|
| 本质 | 服务器常驻 `pi --mode rpc`，加载 pi-coworker 扩展 | 自研路由服务：意图→固定函数→lark-cli |
| 谁做决定 | LLM agent（工具链、多步推理） | 代码规则 |
| 能力上限 | 高（开放任务、多步） | 低（只限已实现意图） |
| 复用 coworker | 全部工具零改造 | 只复用 config + 重写逻辑 |
| 成本 | 高（agent 多工具循环、token） | 低 |
| 并发/运维 | 复杂（每用户会话隔离） | 简单 |
| 安全面 | 大（必须锁工具白名单） | 小（只暴露写死的函数） |

> 决策（已更新）：以**个人本地 Bot 为主**（agent/ 守护程序 `RUN_MODE=local`），同一份代码 `RUN_MODE=server` 部署为公司共享机器人。不再需要 B2 轻量路径——本地 agent 直接复用扩展全部工具。

### 5.2 Bot Agent 守护程序架构（agent/）

```
飞书事件订阅 (lark-event: im.message.receive_v1 / card.action.trigger)
        ↓
┌─────────────── Bot Agent 守护程序 (agent/) ─────────────┐
│ ① 消息适配层：收消息/卡片回调 → 标准化请求                │
│ ② 会话管理器：open_id → agent 会话（pi RPC 子进程）      │
│ ③ 安全网关：按模式工具白名单 · 限流 · 审计              │
│        ↓ prompt（JSONL RPC）                            │
│ ④ pi --mode rpc（pi-coworker 扩展）                  │
│    local 模式：全工具 + 用户身份（本机）                  │
│    server 模式：只读工具 + bot 身份（服务器）            │
└─────────────────────────────────────────────────────┘
```

**关键设计**：
1. **会话隔离**：每用户独立 agent 会话（pi `--session-id`），避免串扰、控成本。
2. **身份按模式**：local 用用户身份（个人数据直接可用）；server 用 bot 身份（`COWORKER_SERVER_MODE=1` 让知识工具走 bot），不代员工直授。
3. **安全按模式**：server 强制禁本地工具 + 只读白名单（否则任何员工可让服务器执行任意命令，不可妥协）；local 默认禁本地工具、`LOCAL_ENABLE_SHELL=1` 显式开启。

## 6. 部署拓扑（个人本地为主）

```
员工本机（核心）
┌───────────────────────────────────────┐
│ 飞书客户端 ←──── 私聊个人 Bot ───┐       │
│   · 问答/申请/入职/卡片          │       │
│                               ↓       │
│  Bot Agent 守护程序（local 模式）       │
│   · lark-cli event consume（个人 Bot）  │
│   · pi --mode rpc（用户身份+全工具）    │
└───────────────────────────────────────┘

公司服务器（可选：全员共享知识机器人）
┌──────────────────────────────────────┐
│ Bot Agent 守护程序（server 模式）        │
│  · 只读工具 · bot 身份 · 7×24          │
└──────────────────────────────────────┘

```

## 7. 成本与取舍（给决策用）

| 形态 | 一次性投入 | 持续运维 | 覆盖 | 推荐时机 |
|---|---|---|---|---|
| A CLI/插件 | 已投入 | 低 | 开发者 | 现在 |
| **个人本地 Bot（核心）** | 低（setup 引导建个人 Bot） | 低（零服务器） | **全员** | **默认** |
| 共享知识机器人（server） | 中（服务器） | 中 | 全员群聊场景 | 需要 7×24 时 |
| C 桌面 GUI | 高（三端/签名/打包） | 高 | 少 | **已降级为可选** |

**提醒**：
- 个人本地 Bot 的代价是**本机需开机 + 守护进程运行**；要 7×24 可用才需要共享机器人（服务器）。
- 本地 Bot 用用户自己的 provider 计费；公司网关是可选优化。
- 若保留 GUI，仅作守护进程托盘/启动器，不做重交互。

## 8. 分期路线图

- **P0（核心，建议先做）**：**个人本地 Bot**（agent/ `RUN_MODE=local`）——个人 Bot 应用接入 + 企业问答 + 权限卡片 + 入职引导；零安装、零服务器、数据在本地。
  - 实现状态：`agent/` 统一双模式守护程序已完成（local 全工具/server 只读均实测；卡片真实发送验证通过；回调/直授已编码）；**个人 Bot 应用接入为上线前置**。
- **P1**：个人本地 Bot 打磨（本地文件能力选开、多轮记忆、个人 Bot 仅本人可用校验）。
- **P2**：可选——公司共享知识机器人（server 模式，7×24）；桌面 GUI 若需要则降为守护进程托盘/启动器。
- **贯穿**：目录/策略中心化（catalog/policy 从中心 Base 下发）、审计同步中心、离职回收（lifecycle）。

## 9. 决策点（已拍板）

1. **交互形态**：**已定 —— 个人本地 Bot 为核心**（后台常驻 agent 在本机，用户在飞书私聊自己的 Bot）；桌面 GUI 降级为可选项；公司共享机器人（server）仅保留给 7×24 全员群聊场景。
2. **GUI 是否立项**：不立项做重交互；如需要只保留守护进程托盘/启动器。
3. **LLM 网关**：本地 Bot 用用户自己的 provider（零成本起步）；公司统一网关为可选优化。
4. **目录中心化**：P1 之前要把 catalog/policy 的下发机制定下来。

## 10. 与本仓库的关系

本仓库继续作为**内核**演进：knowledge/catalog/安全/审计与三个壳解耦。
- 机器人/桌面 GUI 只依赖 `config/`（catalog/knowledge/policy）和 coworker 的检索/申请逻辑。
- 后续可把内核抽成共享库（如 `@coworker/coworker-core`），供 CLI 扩展、GUI、bot 三方调用。

## 11. 飞书机器人交互规格（P0 实现依据）
> 本节定义机器人从员工视角的**具体交互形态**，是 P0 开发的唯一依据。

### 11.1 总体形态

一个飞书应用机器人，员工通过**三种入口**触达，服务端统一收口：

```
入口①：私聊机器人（点开就能问）
入口②：群里 @机器人
入口③：群消息菜单 / 快捷指令

         ↓ 消息事件订阅 (im.message.receive_v1)
    ┌────┴────────────────────┐
    │ 机器人服务（B2 轻量）        │
    │  意图识别 → 路由 → 动作      │
    │  会话状态（多轮上下文）       │
    └────┬────────────────────┘
         ↓ 回复
    文本消息 / 交互卡片 / 审批链接
```

技术栈建议直接复用 **lark-cli**：lark-im（发消息/卡片）、lark-event（收消息/卡片回调）、lark-approval（审批）、lark-base（知识检索）——与内核同源。

### 11.2 交互骨架

1. **收消息**：`im.message.receive_v1` 事件（私聊/群@）。
2. **意图路由**：文本先分类 → `问答 / 申请权限 / 权限盘点 / 入职指引 / 其他`；P0 用关键词规则 + LLM 兜底。
3. **动作执行**：复用 knowledge 检索 / catalog 权限目录 / perm_scan 逻辑。
4. **回复**：文本消息（带 @回复）或交互卡片（可点击按钮）。
5. **卡片回调**：按钮触发 `card.action.trigger` → 服务端处理 → **原地更新卡片**（loading → 结果）。
6. **会话状态**：按 `open_id → 上下文` 存多轮会话（内存/Redis/Base），支持追问。

### 11.3 四种交互形态

#### 形态①：企业问答（最高频）—— 文本 + 来源卡片

```
员工私聊机器人：
┌─────────────────────────────┐
│ 我：报销流程是什么？              │
└─────────────────────────────┘
┌─────────────────────────────┐
│ 💬 报销流程（节选）               │
│ 1. 提交报销单 …                │
│ 2. 部门负责人审批 …             │
│ 3. 财务复核打款（T+3）          │
│ 📎 来源：《财务日常指南》          │
│    🔗 打开原文   [追问] [没看懂] │
└─────────────────────────────┘
```

规则：群内 @回复提问者；找不到→明说“未找到”+关键词建议；敏感问题（薪资/个人信息）→拒绝并提示合规边界；一律附来源。

#### 形态②：权限申请 —— 按钮卡片（一键发起）

```
员工：申请研发知识库权限
┌─────────────────────────────┐
│ 🔐 研发知识库（wiki_engineering）│
│ 授予方式：自服务直授              │
│ 你当前：未具备                   │
│   [一键申请]   [查看我的权限]    │
└─────────────────────────────┘

点[一键申请] →
┌─────────────────────────────┐
│ 🔐 研发知识库                  │
│ ⏳ 已提交，处理中…              │
│ ① 直授开通  ② 通知你           │
│ [刷新状态]                     │
└─────────────────────────────┘
完成后卡片自动更新：✅ 已开通，点此进入知识库
```

规则：走审批的权限 → 按钮改为打开**飞书原生审批表单**（员工在飞书内走完审批，bot 只推状态卡片）；自服务直授 → 卡片回调触发开通并更新卡片。

#### 形态③：权限盘点 —— 表格卡片

```
员工：我能访问哪些知识库？
┌─────────────────────────────┐
│ 📋 你的知识权限                 │
│ 知识库            角色         │
│ 公司全员知识库     非成员仅可见   │
│ 技术标准体系       非成员仅可见   │
│ 硬件交付物模版库   admin        │
│ 可检索文档：约 176 篇           │
│   [申请缺失权限]  [去知识库]     │
└─────────────────────────────┘
```

#### 形态④：入职引导 —— 图文步骤卡片

```
员工：入职指引
┌─────────────────────────────┐
│ 🎒 入职三步曲                  │
│ ① 登录飞书（员工号）            │
│ ② 下载公司桌面助手（GUI）        │
│    → 扫码登录，自动开通权限      │
│ ③ 必读文档                    │
│    🔗 新员工入职必读            │
│   [我完成了]  [联系 IT]        │
└─────────────────────────────┘
```

> 边界：安装/扫码登录是**本机动作**，bot 只做“指引 + 链接”，真正执行在桌面 GUI/网页完成——这是 bot 与 GUI 的分工。

### 11.4 必须解决的工程点

1. **多轮会话状态**：`open_id → 上下文` 存储（内存/Redis/Base），支撑追问。
2. **意图路由**：关键词规则 + LLM 兜底；分类失败时回默认帮助卡片。
3. **卡片回调安全**：回调校验（token/签名）、按钮幂等、防重复开通。
4. **审计**：所有问答/申请动作写入审计（与内核共用 `~/.coworker/audit` 或中心 Base）。

### 11.5 分工边界（回顾）

| 动作 | 机器人（bot 身份） | 桌面 GUI（本机用户身份） |
|---|---|---|
| 读公司百科/制度 | ✅ 服务端只读 | ✅ |
| 权限申请 | 发审批链接/卡片，不能代加成员 | ✅ 直授/审批 |
| 查看“我的”资源 | ⚠️ 需 OAuth | ✅ |
| 本地文档处理 | ❌ | ✅ |
| 入职扫码登录 | ❌ 仅指引 | ✅ |
